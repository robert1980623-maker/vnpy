- 滞后 100-300 小时: 4 只股票 (2026-03-13)
- 滞后 48-100 小时: 6 只股票 (2026-03-16)

### 1.2 根本原因分析

#### 1.2.1 数据下载任务问题

**当前配置** (`batch_download_enhanced.py`):
```python
TOTAL_STOCKS = 20  # 只下载 20 只股票
BATCH_SIZE = 5     # 每批 5 只
BATCH_DELAY = 30   # 批次间隔 30 秒
```

**问题**:
1. ❌ 只下载 20 只股票，但数据目录有 47 只文件
2. ❌ 股票列表来自沪深 300 前 20 只，与持仓不匹配
3. ❌ 持仓 13 只股票，但下载目标不一致
4. ❌ 没有增量更新机制，每次都全量下载

#### 1.2.2 监控与修复脱节

**当前架构**:
```
data_freshness_monitor.py → 只检查，不修复
stale_data_updater.py → 只更新持仓，不检查全部
batch_download_enhanced.py → 只下载固定 20 只
```

**问题**:
1. ❌ 监控器发现滞后但不触发修复
2. ❌ 修复脚本独立运行，不依赖监控结果
3. ❌ 没有闭环反馈机制

#### 1.2.3 定时任务配置分散

**当前 Cron 配置**:
```bash
# 系统 crontab
0 17 * * *  数据下载 (17:00)

# OpenClaw cron (config/data_freshness_cron.json)
0 * * * *    数据新鲜度检查 (每小时)
30 16 * * *  陈旧数据自动更新 (16:30)
```

**问题**:
1. ❌ 多个 cron 系统并存 (系统 cron + OpenClaw cron)
2. ❌ 任务时间冲突 (16:30 更新 vs 17:00 下载)
3. ❌ 凌晨数据下载任务缺失或失败
4. ❌ 没有失败重试和告警机制

#### 1.2.4 数据源策略问题

**当前配置**:
```python
DATA_SOURCE_PRIMARY = "tushare"
DATA_SOURCE_BACKUP = "akshare"
```

**问题**:
1. ⚠️ Tushare token 可能过期或未配置
2. ⚠️ 数据源切换没有日志记录
3. ⚠️ 没有第三数据源 (Baostock 未启用)

### 2.3 数据质量检查

#### 2.3.1 质量检查维度

| 维度 | 检查项 | 阈值 | 严重级别 |
|------|--------|------|----------|
| **时效性** | 数据滞后时间 | < 24h | Critical |
| **完整性** | 必需字段缺失 | 0 缺失 | Critical |
| **准确性** | 涨跌幅异常 | > 板块限制 | Warning |
| **连续性** | 交易日缺失 | > 3 天 | Warning |
| **一致性** | 量价匹配 | 异常比率 | Info |

#### 2.3.2 质量检查流程

```python
质量检查流程:
  1. 加载数据文件
  2. 检查文件存在性和大小
  3. 解析最后 N 行数据
  4. 验证字段完整性
  5. 检查日期连续性
  6. 计算涨跌幅验证
  7. 生成质量评分
  8. 输出检查报告
```

#### 2.3.3 质量评分算法

```python
def calculate_quality_score(freshness, completeness, accuracy, continuity):
    """
    质量评分 (0-100)
    
    权重:
    - 时效性 (freshness): 40%
    - 完整性 (completeness): 25%
    - 准确性 (accuracy): 25%
    - 连续性 (continuity): 10%
    """
    score = (
        freshness * 0.40 +
        completeness * 0.25 +
        accuracy * 0.25 +
        continuity * 0.10
    )
    return score * 100

质量等级:
  - A (90-100): 优秀，无需操作
  - B (75-89):  良好，关注即可
  - C (60-74):  一般，需要改进
  - D (<60):    差，立即修复
```

### 2.4 监控告警机制

#### 2.4.1 监控指标

| 指标 | 阈值 | 告警级别 | 通知方式 |
|------|------|----------|----------|
| 数据新鲜率 | < 95% | Warning | 企业微信 |
| 数据新鲜率 | < 80% | Critical | 企业微信 + 邮件 |
| 单只股票滞后 | > 48h | Warning | 企业微信 |
| 单只股票滞后 | > 72h | Critical | 企业微信 + 邮件 |
| 下载失败率 | > 20% | Warning | 企业微信 |
| 下载失败率 | > 50% | Critical | 企业微信 + 邮件 |
| 质量评分 | < 60 | Critical | 企业微信 + 邮件 |

#### 2.4.2 告警升级机制

```
告警升级流程:
  
  Level 1 (Warning):
    ├─ 企业微信通知
    ├─ 记录日志
    └─ 等待自动修复
  
  Level 2 (Critical):
    ├─ 企业微信 + 邮件
    ├─ 触发自动修复
    ├─ 记录详细诊断
    └─ 1 小时后未恢复 → Level 3
  
  Level 3 (Emergency):
    ├─ 多次通知 (间隔 30 分钟)
    ├─ 触发紧急补采
    ├─ 生成诊断报告
    └─ 通知管理员介入
```

#### 2.4.3 自动修复策略

```python
自动修复策略:

  触发条件:
    - 数据新鲜率 < 90%
    - 单只股票滞后 > 48h
    - 下载任务失败
  
  修复动作:
    1. 尝试重新下载 (最多 3 次)
    2. 切换数据源重试
    3. 标记问题股票，跳过继续
    4. 生成修复报告
  
  修复验证:
    - 修复后立即检查新鲜度
    - 验证数据完整性
    - 更新监控状态
```

| 术语 | 定义 |

| 新鲜度 | 数据最后更新时间距当前的时间差 |
